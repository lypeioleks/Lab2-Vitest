## 1. Мета роботи
Набути навичок розроблення модульних тестів для бізнес-логіки: добирати матчери відповідно до типу даних, проєктувати вхідні дані за класами еквівалентності та межовими значеннями, застосовувати параметризовані тести, вимірювати й інтерпретувати покриття коду.

## 2. Аналіз вхідних умов

| Функція | Класи еквівалентності | Межові значення / перевірки |
|---|---|---|
| `calcSubtotal` | порожній масив; коректні позиції; від’ємна ціна; некоректна кількість | `qty = 0`, `1`, `-1`, `1.5`; `price = 0`, `-0.01` |

| `calcOrderTotal` | платна/безкоштовна доставка; знижка переводить суму нижче порога; помилка нижнього рівня | після знижки сума нижче, рівно або вище `1000` |
| `validateCoupon` | правильний формат; малі/зайві/недостатні літери; неправильний роздільник; нецифрові символи; зайві пробіли | довжина цифрової частини `3`, `4`, `5`; рівно три великі латинські літери та чотири цифри |

## 3. Реалізація та тести показового прикладу
Файл `src/order.ts` містить реалізацію функцій замовлення за специфікацією лабораторної роботи. Реалізацію показового прикладу не змінено. Тести розміщені у `tests/order.test.ts`.

Використано:
- `toBe` для точних цілих чисел, булевих значень і тарифу доставки;
- `toBeCloseTo` для дробових грошових розрахунків;
- `toThrow` для перевірки винятків; у `expect` передається функція, а не результат її виклику;
- `it.each` для наборів однотипних вхідних даних.

Вхідні дані підібрано за класами еквівалентності та методом граничних значень. Очікувані результати вказані явно, а не обчислюються повторно тією самою формулою.

## 4. Індивідуальне завдання — варіант 3

### Специфікація
`validateCoupon(code)` перевіряє формат промокоду. Допустимий формат: три великі латинські літери, дефіс і чотири цифри, наприклад `ABC-1234`. Функція повертає `true` для правильного формату та `false` для неправильного рядкового формату. Якщо замість рядка передано значення іншого типу (зокрема, під час виклику з JavaScript), викидається `INVALID_COUPON_INPUT`.

### Реалізація

```ts
export function validateCoupon(code: string): boolean {
  if (typeof code !== 'string') throw new Error('INVALID_COUPON_INPUT');
  return /^[A-Z]{3}-[0-9]{4}$/.test(code);
}
```

### Тести
Файл `tests/validateCoupon.test.ts` містить параметризовані перевірки коректних і некоректних кодів, а також граничних довжин цифрової частини: 3, 4 і 5 цифр. Перевіряються малі літери, неправильна кількість літер, відсутній дефіс, неправильна кількість цифр, літери серед цифр, пробіли та кириличні символи. Окремо перевіряється виняток `INVALID_COUPON_INPUT` для аргументу не рядкового типу.

Форматний рядок перевіряється регулярним виразом, а некоректний тип аргументу — окремою умовою з власним кодом помилки. Фактичний відсоток покриття необхідно підтвердити запуском `npm run coverage` у середовищі з установленими залежностями.

## 5. Покриття коду та експеримент
Для вимірювання покриття налаштовано провайдер V8 і звіти `text` та `html`. Поріг для рядків, функцій, гілок і операторів встановлено на 90 %. HTML-звіт створюється у `coverage/index.html`.

Експериментальний тест без твердження:

```ts
it('виклик без перевірки результату', () => {
  calcOrderTotal([{ sku: 'SKU-1', price: 100, qty: 1 }], 'silver');
});
```

Такий тест може збільшити покриття рядків/гілок, оскільки виконує код, але не перевіряє правильність результату. Тому покриття показує, яка частина коду була виконана, але саме по собі не доводить якість тестів. Після фіксації показників експериментальний тест потрібно видалити. **Числові показники експерименту не наведено**, оскільки в поточному середовищі залежність Vitest не встановлена й прогін не відбувся.

## 6. Взаємне рецензування
Нижче наведено шаблон рецензії, який потрібно адаптувати після перегляду роботи конкретного однокурсника:
1. Перевірити, чи охоплено значення на межі та по обидва боки від неї; за відсутності таких тестів додати конкретні граничні приклади.
2. Перевірити, чи задані очікувані результати явними константами, а не повторенням формули з реалізації.
3. Перевірити відповідність матчерів типам даних (`toBe` для точних значень, `toEqual` для структур, `toBeCloseTo` для дробових чисел) і відсутність тестів без тверджень.

## 7. Відповіді на контрольні питання

**1. Що таке класи еквівалентності та аналіз межових значень?**  
Класи еквівалентності — групи вхідних даних, для яких очікується однакова поведінка. Аналіз межових значень перевіряє значення безпосередньо до, на та після межі. Наприклад, для безкоштовної доставки перевіряються 999, 1000 і 1001.

**2. Чому для грошових обчислень не можна застосовувати `toBe`?**  
Через особливості представлення дробових чисел у форматі з рухомою комою можливі малі похибки. Для таких результатів використовують `toBeCloseTo`.

**3. Як правильно перевірити виняток?**  
Передати функцію, яка викидає виняток: `expect(() => calcSubtotal([])).toThrow('EMPTY_ORDER')`. Типова помилка — викликати функцію безпосередньо всередині `expect`, через що виняток виникне до виконання матчера.

**4. Відмінність між `toBe` і `toEqual`?**  
`toBe` перевіряє точну тотожність значень (для об’єктів — посилання), а `toEqual` порівнює структуру об’єктів і масивів. Наприклад, два різні об’єкти `{ a: 1 }` не пройдуть `toBe`, але пройдуть `toEqual`.

**5. Чому не можна обчислювати expected тією самою формулою?**  
Якщо реалізація містить помилку у формулі, тест із тією самою формулою повторить цю помилку й може пройти. Очікуване значення потрібно визначати незалежно та задавати явно.

**6. Що показує покриття гілок і чим воно інформативніше за покриття рядків?**  
Покриття гілок показує, чи були виконані альтернативні напрямки умов (true/false). Рядок може виконатися, але одна з гілок умови залишитися неперевіреною.

**7. Приклад тесту, який підвищує покриття, але не має цінності.**  
Тест, що лише викликає `calcOrderTotal(...)` без жодного `expect`. Він виконує код, але не перевіряє результат. Отже, високий відсоток покриття не гарантує якісних перевірок.

**8. Для чого потрібні параметризовані тести та коли вони недоречні?**  
`it.each` дає змогу перевірити багато наборів даних одним шаблоном і прибирає дублювання. Він недоречний, коли сценарії мають суттєво різну логіку підготовки або різні очікування, які краще описати окремими тестами.

**9. Що станеться, якщо не досягнуто порога покриття?**  
Якщо пороги налаштовані в конфігурації Vitest, прогін із показниками нижче порога завершується помилкою та ненульовим кодом завершення.

**10. Яку поведінку фіксує третій тест `calcOrderTotal`? Це дефект чи рішення?**  
Знижка може зменшити суму з 1050 до 945, тобто нижче порога безкоштовної доставки. Тоді додається 60 за доставку й підсумок становить 1005. Тест фіксує поведінку наявної реалізації. Чи є це дефектом, залежить від бізнес-вимог; у межах лабораторної це свідомо зафіксована поведінка, а не самостійно виправлена помилка.
